What actually happened

Two beads tasks went through the molecular workflow — one task-execute molecule and one bug-triage molecule, cooked separately because bug and non-bug types must not share an epic. Both finished, landed, and pushed. The interesting part of the session was not the code; it was that three separate measurements overturned plans that all read as reasonable on paper.

Each time the correction ran the same direction: the intended change got smaller, and the confidence in it got higher. That pattern is the report's main finding.

Task 1 — neograph-qtfof.13: derive the provider instead of asking for it

The gap

to_agent_spec() emitted LlmConfig.api_provider=None for every LLM-bearing node, and pyagentspec's own adapters refuse such an artifact. 72 of the 88 unexecutable matrix cells traced to exactly that. The previous ticket had shipped an opt-in api_provider= string, which is correct but uniform — it cannot express a construct whose tiers resolve to genuinely different providers.

What research established

QuestionAnswer, verified against source
Is llm_factory reachable from a bare Construct?No — LlmRuntime is built inside compile(). But lint() and Node.run_isolated() already accept llm_factory=, so this is the fourth instance of an existing convention, not a new seam.
What is the provider mapping?There is no enum to map onto. api_provider is a free-form Optional[str], and all five shipped adapters dispatch a bare LlmConfig on the single literal "openai" and raise otherwise. Other providers are represented by subclasses.
Precedence?Explicit wins. With a one-row table it stays the only route for an unclassifiable factory.
Does import stay symmetric?Yes — from_agent_spec already discards concrete provider info, so the derived value must never enter the IR.
This reframed the ticket. Deriving "anthropic" from a ChatAnthropic would emit an artifact that still fails to load, with a worse message than today's honest None. The useful derivation is one row, and everything else stays None until neograph grows subclass lowering.

The correction that mattered

The plan that reached the maintainer carried a local OpenAI-compatible stub server, a round-trip marker change, and two escalated scope questions. The maintainer's objection was blunt and correct: at compile time we already have the provider, and we know what fast resolves to — this is a standard LLM configuration.

They were right. The feature is five steps: accept the kwarg, resolve the tier through the existing _get_llm, read provider/model/base-url off the resolved client, emit them at the single construction site, and record the tier so round-trip still restores it. Two things had been inflated and were withdrawn:

  • The api_key finding was rated HIGH on the grounds that a derived config cannot authenticate. That is how every config export works — you do not ship the secret. Not a defect.
  • The stub server was never about the feature. It existed so a test tier could prove the artifact executes.

And the stub turned out to be unnecessary: the api_provider failure is a construction failure inside the adapter, before any network call. So the gap is measurable at load, with no endpoint and no credentials.

Closing evidence — population, not sample

api_provider-blocked cells targeted : 72
still refused over api_provider      :  0
past the third-party dispatch gate   : 72   (all then stop on: Missing credentials)

Pinned as a standing test that reads its own population from EXEC_EXEMPT, so the set cannot drift out from under it. The first version of that tier covered 4 representative cells; reporting "72" off a 4-cell proof would have been the exact self-certification the ticket's notes forbid.

What the file-size ratchet forced

_agent_spec.py was at its exact ceiling. The rule says verbatim that raising the number is not a remedy, splitting the file is — so _lower_construct_item moved to its own module, taking the file from 694 to 479, i.e. under 500, which deletes its allowlist entry rather than lowering it. flow_export is injected as a parameter to break the resulting cycle — the exact precedent AGENTS.md names.

Task 2 — neograph-35mur: the boundary that answered a different question

The bug, reproduced exactly

Construct.output=X was not a wire but a search: walk the child's final state in reverse, return the first isinstance match. That state holds more than the child computed — a forwarded context= field, the input port, framework keys — and context fields are appended after node output fields.

the LLM computed : Case(docket='D-1', readings=5, claims=3)
boundary returned: Case(docket='D-1', readings=5, claims=0)   <- the opening case

Same construct, one declaration apart:

context=None        -> boundary = SETTLED
context=['opening'] -> boundary = OPENING     no error, exit 0
The DX crime is the direction of the coupling. context= is an input declaration. Adding one silently re-pointed an unrelated output. The reporter's cost was a type invented purely to be type-distinct, whose docstring had to say "distinctness is the whole of its job" — against this codebase's own rule about types that only move shapes.

The measurement that changed the design

The ticket's acceptance criteria said the type scan should refuse when more than one value matches. The review instrumented the real scan across the whole suite before anyone wrote code:

output-boundary resolutions : 270
ambiguous (>1 type match)   :  26   (9.6%)
item-order rule AGREES      :  24
item-order rule DISAGREES   :   2   <- and both ARE this bug

So refusing would have turned 24 currently-green ordinary resolutions into hard failures — review → revise, write → improve, the canonical refine chain — and pushed authors toward exactly the invented-for-distinctness type the ticket exists to abolish.

Two maintainer decisions

DecisionChosenWhy it holds
A. Ambiguous or ordered? Ordered — restrict eligibility to the construct's own declared items, last one wins A forwarded context field is not an item, so it can never win. Fixes the bug with a 2-of-270 delta and no API change. Converges with resolve_end_node_sources, which already answers this positionally.
B. How to spell the explicit port? Separate field — output_from="settle" Portal.output and ConstructSpec.output already use a str for a type name. One spelling, two meanings, on sibling fields is the same duplicated-authority condition that produced the bug.

What survives, deliberately

The type scan is not deleted, for two reasons that are not oversights:

  • A multi-arm branch's boundary is legitimately satisfied by a different node per arm. One name cannot express that.
  • Portal mode-(b) dispatch invokes a flow emitted at runtime, whose item names cannot be known at assembly — there is no eligibility set to pass.

Reading the acceptance as "delete the scan" would have broken Portal. That escape hatch is now pinned to its one legitimate caller by a guard verified to fail on an injected second one.

Systemic finding: one heuristic, four sites, two contradictory rules

The trace-similar atom returned more value than the fix. The same disease — choose which of several state values is meant by isinstance-matching over a bag — has four implementations, and they do not agree:

The exported Agent Spec artifact computes a different answer than the pipeline it was exported from. A portability defect stacked on a correctness one, and neither surface complains. Filed as neograph-t1nbp at P1.

Mistakes made in this session

Recorded because the pattern is more useful than the individual slips.

  • Missed a consumer when threading the resolver. _agent_spec_portal.py was in neither the research nor the review consumer list and broke at the first full gate. This is the AGENTS.md Portal retrospective repeating verbatim — treat any such list, including this one, as provisional until re-verified by grep.
  • Overwrote an existing file without looking. Used cat > on _agent_spec_types.py, which already existed. Restored from git, no damage, new module renamed — but the check should have come first.
  • Ran ruff format over the whole package, touching 20 unrelated files. Reverted all of them.
  • Shipped a vacuous test in the first reproduction: pytest.raises(Exception, match="nosuchnode") passed because a Pydantic type error happened to contain the string. It would have kept passing if the feature were never built. Tightened to demand neograph's own ConstructError.
  • Declared a disease scan "semantic" but ran three syntactic commands, and so missed a fifth resolver (resolve_end_node_sources, which answers the same question positionally). Caught by the review, not by me.
  • Broke dict-form outputs with the first eligibility helper — those write {node}_{key}, not {node}. Caught by an unrelated existing test, not by the new boundary tests.
